# 基于系统可用内存保留比例的 Adaptive 设计

状态：已实施，Windows 功能验证通过；参数效果的验证边界见第 15 节

编写日期：2026-09-12

改造基线：`7b76ce3b7`，独立 CPU 控制已在该提交中实现。第 11 节参照 `DataCodecCpuController::Reset / Advance / Estimate` 的 K 机制；本轮在该基线上实施内存保留目标、Km 观测、存储准入及 Qt 适配。以下路径均相对于 DataCodec 目录；Qt 路径相对于仓库根目录。源码位置通过文件与符号定位。

## 1. 目标与承诺

内存 Adaptive 以“尽力保留指定比例的系统可用物理内存”为唯一自动调节目标。默认保留比例为 20%，分母采用操作系统报告的系统物理内存总量。

```text
T = 系统物理内存总量
r = 目标保留比例
R = ceil(T × r)
A = 系统当前可用物理内存
```

20% 表示期望系统至少保留 `R` 字节可用内存。实际数据需求较小时，允许系统保留更多可用内存。控制器仅为真实申请开放容量，不为接近目标主动建立缓存、预读或预分配数据。

控制对象仍为现有清单中的 DataCodec 自有存储、工作缓冲及其准入。系统观测包含其他程序、宿主、第三方库和操作系统自身的影响。借用数据、宿主输出和第三方内部内存继续遵守现有豁免边界。

本模式承诺有界的准入、明确的等待和失败路径，以及对系统余量偏差的响应。保留比例允许短时偏离。它不承诺整个进程物理占用的精确硬上限，也不承诺单靠 DataCodec 就能恢复由其他程序造成的余量不足。

基础编码块、数据格式和解码基础粒度保持固定。批次数和在途数量属于执行机制，不修改文件中的基础块以适应设备。

## 3. 模式与参数约定

在 `CodecResourceParams` 中新增：

```cpp
// Adaptive 的系统可用物理内存保留比例，省略时采用 0.20
std::optional<double> targetAvailableMemoryRatio;
```

| 内存模式 | `ownedStorageLimitBytes` | `targetAvailableMemoryRatio` | 运行行为 |
|---|---|---|---|
| Fixed | 可填写，省略时沿用设备启动默认；零保持禁止新增正容量的语义 | 必须省略 | 本次请求使用固定字节额度 |
| Adaptive | 必须省略 | 可填写，省略时采用 0.20 | 按系统保留目标生成运行时字节额度 |
| Unlimited | 必须省略 | 必须省略 | 不设置 DataCodec 字节额度 |

比例必须有限且满足 `0 <= r < 1`。`r = 0` 仍执行原生压力、运行环境能力与实际分配失败检查。NaN、无穷大、越界比例和模式参数冲突通过既有参数校验/failure 路径报告。

Adaptive 不再配置一个固定的 DataCodec 字节天花板。底层继续存在表示能力和运行环境能力的边界，见第 4 节。线程参数独立校验，不将内存保留比例换算成允许线程数。

模式和比例在请求启动前确定。运行时由内部控制器调整额度、准入及缓存保留状态。已有 lazy decode 会话保留启动配置，并在新的实际请求开始时重新采样。请求闲置期间不启动后台缓存淘汰任务。

Qt 编解码共用资源控件增加“系统可用内存保留比例”输入，Adaptive 时显示，初始显示 20%。Fixed 显示原字节额度输入，Unlimited 禁用内存数值输入。保存仅持久化当前模式有效参数，旧配置中的 Adaptive 字节数不自动换算成比例。加载旧 Adaptive 配置时使用 20% 的新默认并清除无效字段，记录配置版本迁移。

## 4. 控制量、确定容量与系统观测

| 符号 | 含义 | 用途 |
|---|---|---|
| `T, A, R` | 物理总量、系统可用量、目标保留量 | 物理余量反馈 |
| `B` | 同一 `ResidentByteBudget` 中有效 lease 的 `reservedBytes` | 容量承诺一致性和下一次预约计算 |
| `M` | 当前发布的受控存储字节额度 | 决定新的容量预约能否获准 |
| `U = max(0, M - B)` | 尚未预约的许可空间 | 判断下一笔申请是否需要扩张额度 |
| `N` | 下一笔新预约的确定字节数 | 必需申请与批次准入 |
| `C` | 当前绝对容量能力边界 | 限制表示范围和环境明确能力 |
| `J` | 本次系统样本报告的环境剩余容量 | 限制允许的新增长 |
| `F` | 本次样本下允许考虑使用的余量 | 决定增长窗口和必需申请是否具备条件 |

`B` 是执行机制自己已经发出的精确容量承诺。它不等于 RSS，也不等于完整的 DataCodec 内存审计结果。允许使用 `B` 校验预约算术；禁止由审计合计、`allocatedStorage.liveBytes`、宿主内存估算反推系统余量。

申请 `N` 的口径必须与现有预约一致：

- 解码工作区先取得可复用 backing，再使用仍需新分配的确定区域容量。
- 连续存储按其实际所需容量申请。
- 扩容复制期间旧数组仍被持有时，`B` 包含旧数组，`N` 包含新数组全容量，不把 `N` 错写为新旧容量之差。
- 共享存储的 lease 只记一次；拆分、合并、移交遵循已有所有权规则。
- 只知道上界的计算布局应明确标记为预先承诺的容量上界，不把它写入实际物理占用统计。

物理保留目标的分母始终使用 `physicalTotalBytes`。进程/Job 限制不改变 `T`，其剩余量也不替换日志中的 `A`。

```text
C = min(T, size_t 可表示容量, 已知的进程/Job/地址空间绝对容量限制)
J = min(本次样本中已知的提交/进程/Job/地址空间剩余量)
```

没有报告的环境剩余项不贡献一个虚构数值。现有 `hardLimitBytes`、`hardRemainingBytes` 可用于表示这些已知限制的合并结果；物理观测字段继续独立保留。

有效物理样本必须满足 `T > 0`、`0 <= A <= T`、时间戳有效且年龄不超过 1 s。Windows 启动时无法取得有效物理样本，直接报告 `memory-observation-unavailable`，不静默切换为 Fixed 或使用虚构预算。运行期间样本失效时关闭新工作准入、停止增额，进入以 `SampleUnavailable` 为原因的排空/等待；恢复采用第 7 节的持续健康条件，持续失效采用同一个 30 s 截止规则。WASM 当前缺少这些物理观测时不提供本方案的 Adaptive，Fixed 与 Unlimited 保持原有适用范围；本轮不开展 WASM 实施和验证。

`C` 是运行时能力字段，不是模块份额分配。检测到 `T` 或明确环境能力变化时，在同一个发布事务中更新 `R`、水位和 `C`。已有 `B > C` 时先停止新增并排空；剩余必需容量仍超界时失败。禁止要求已经存在的 lease 瞬间消失。

## 5. 水位与首版参数

本节规定首版实现起点，数值尚未经过本方案的 Windows 验收。参数集中放入 `DataCodecResourceController.h` 的内存控制常量区域，禁止各模块自行设置系数。

| 参数 | 首版值/计算方式 | 含义 |
|---|---|---|
| 默认保留比例 | 0.20 | 用户可覆盖的目标 |
| 采样周期 | 250 ms | 复用现有内存采样节奏 |
| 样本最大年龄 | 1 s | 防止过期余量用于新增长 |
| 恢复滞回 `h` | `min((T-R)/2, clamp(T/200, 16 MiB, 256 MiB))` | 目标附近的缓冲带 |
| 收缩水位 `L` | `R` | `A < L` 时立即停止新工作准入 |
| 恢复水位 `H` | `R + h` | 持续达到后恢复 |
| 严重压力 | 原生 Critical，或 `A < R/2` | 加强诊断，立即要求回收 |
| 原生 Low | 直接进入压力处理 | 不等待普通持续时间确认 |
| 普通低余量确认 | 500 ms | 确认后回收可选留存 |
| 恢复确认 | 连续 2 s | 要求新鲜样本均达到恢复条件 |
| 增长系数 `Km` | 请求初始值 1/2；按第 11 节短窗口估计及后续观测更新 | 控制可提前开放的许可窗口 |
| 内存响应修正比例 `αm` | 1/2 | 将观测响应 `gm` 换算成 `Km`，集中声明的保守程度参数 |
| `Km` 取值范围 | `[0.025, 1]` | 每次更新均限幅，沿用当前 CPU 增益限幅的首版取值 |
| K 观测窗口 | 250 ms，前后各一段 | 使用原内存采样时钟，目标约 500 ms 完成一组短观测 |
| K 首次测量期限 | 1 s，从进入 Measuring 起算 | 到期结束本次测量，不阻塞正常任务等待 K |
| K 首次小幅调整 | 下一笔普通增长的提前许可部分乘以 0.75，仅一次 | 复用真实需求，完整保留 `N` 的原子申请分支 |
| 正常增长步长基准 `S` | `max(1 MiB, T/16)` | 控制一次提前开放的额度 |
| 正常增额观察间隔 | 至少 500 ms，并满足第 6 节事件条件 | 避免未生效的连续授权 |
| 压力后扩张冷却 | 2 s，恢复时同时启动 | 冷却内仅允许串行必需推进 |
| 等待截止时间 | 30 s | 必要申请或压力状态长期无法恢复时失败 |

增长时取当前及上一份连续新鲜样本的较小可用量作为 `A_grow`。启动仅有一份有效样本时使用该样本。收缩直接采用当前新鲜样本和原生压力事件，避免平滑延迟掩盖下降。

```text
F = min(max(0, A_grow - H), J, max(0, C - B))
```

所有乘法、加法、浮点比例转换均检查有限性和范围。字节差值使用饱和减法，避免无符号下溢。`h` 的计算在 `r` 接近 1 时仍保持 `H <= T`。

## 6. 增长算法：有需求的许可窗口

### 6.1 启动

在开始重型申请前取得有效物理样本，计算 `T/R/H/C/F`。已有会话存储包含在 `B` 中；它的物理影响已经包含在系统可用量中。

```text
W = min(floor(Km × F), S)
M初始 = min(C, B + W)
```

这里发布的是分配许可，不预分配 `W` 字节。不重复把已有 `B` 从 `A` 中扣除。启动就处于低余量、原生压力或有效环境剩余量不足状态时，先保持 `M = B` 并关闭新工作准入。

每次顶层请求以名义 `Km = 1/2` 开始执行。第 11 节的观测与正常工作同时进行；启动流程无需等待估计结果。已有会话存储继续由 `B` 表达，上一请求的 Km 估计不跨请求沿用。

### 6.2 普通运行

M 的扩大由确定的必要申请触发。仅有“后面还有块”不构成提前增额的理由。

driver 发布 `N` 和申请所有者/阶段标识。若槽位、CPU 准入、内存准入以及现有 `M` 已满足要求，按现有路径预约，无需调用平台 API。平台采样集中在控制线程，禁止每次容器分配都执行系统查询。

当 `N > U`，控制器使用新鲜样本决定是否打开下一份许可窗口。设本次批准的未预约空间为 `W`：

```text
必需申请条件：N <= F
W = min(F, max(N, min(floor(Km × F), S)))
M新 = min(C, B + W)
```

公式以同一时点的 `B` 为基准，避免把旧的未使用许可再次叠加。`N` 是整笔新的容量预约；物理余量检查不能只检查 `N-U`，因为 `U` 尚未代表已经消耗的物理内存。

`N > floor(Km × F)` 或 `N > S` 时，只要 `N <= F`，就允许按确定的 `N` 批准该笔必需申请。增长系数和普通步长只控制提前开放的余量，不能让一笔已满足保留目标的原子申请永远等待。这是增长算法的正式分支。

公式中的 `Km` 读取当前已发布的增益。第 11 节的一次小幅调整仅作用于 `min(floor(Km × F), S)` 这一项。增益更新影响后续许可决策，不撤销已有 lease，不单独触发增额，不修改 `N<=F` 的条件。

`N > F` 时不给出足额许可。driver 保持需求、继续消费可完成结果并解除可选引用，等待新样本或真实释放事件。等待不能把 `R` 自动改小，也不能把模式切到 Unlimited。

### 6.3 防止额度空转增长

保留一个 `grantEpoch`，记录最近一次增额时的申请、基准 `B`、样本序号和关联工作单元。下一次普通增额需满足：

1. 有一笔新的必要申请，现有 `M` 无法满足。
2. 上次额度已经用于其目标预约，或目标申请已经明确取消。
3. 上次关联工作已越过本身的完成/退休观察边界，并取得边界之后的新样本。
4. 达到最小增长间隔，未处于压力排空或信号失效状态。

连续的阶段必需存储可能必须共存，后一个申请是完成当前阶段的前提。此类申请由 driver 明确标记为 `RequiredContinuation`，在当前没有会被自己阻塞的活跃终端任务时，取得前一笔分配准备完成之后的新样本，直接执行上面的 `N <= F` 判断。它无需等待这些共存数据释放，也不追加普通预留窗口，使用 `W = N`。

`RequiredContinuation` 不能由 allocator、worker 自动推断，调用点必须在申请前明确声明其生命周期。借此避免“等自己的后继释放内存”的依赖环。

可选缓存不触发增额或等待。它只使用已开放的剩余额度，并遵守独立的可选保留状态。

K 测量复用上述申请事件和采样时钟，遵守本节全部准入条件。没有新的合法增长时，在测量截止前等待正常申请；截止时记录 TimedOut。不为凑齐样本增加申请、跨过完成边界或缩短普通增长间隔。

### 6.4 缩小尚未使用的许可

新样本显示可用于增长的余量减少时，可以收回未预约许可，将 `M` 下调至 `min(M, B + F)`。有效 lease 保持有效，现有数组不移动。

该动作只取消未来申请权限。日志分别记录许可减少量与之后实际观察到的系统可用内存变化。不得把许可减少量报告成释放了同样大小的物理内存。

工作单元仍有需要分配的确定内存时，应在准入阶段包含其完整受控需求或提前获得 lease。未被承诺覆盖的终端必需增长走第 9 节的失败路径。

## 7. 压力状态机与收缩

在现有 `Normal / Drain / Hold` 状态基础上，明确增加 `Recover`，压力等待与样本失效通过原因字段区分。

| 状态 | 新工作准入 | 已接纳工作 | 额度/缓存动作 | 转移条件 |
|---|---|---|---|---|
| Normal | 允许按槽位与额度检查 | 正常执行和提交 | 按真实需求增额，允许已有可选策略 | `A<R`、原生压力、信号失效或明确环境约束触发 Drain |
| Drain | 关闭 | 已有 lease 支持的工作继续完成，结果继续提交 | 停止增额，收回未预约许可；确认压力后禁用并回收可选留存 | 到达可安全停留的申请边界后进入 Hold；余量恢复则进入 Recover |
| Hold | 关闭 | 清理与取消保持可执行 | 保持当前必需数据，继续采样；不反复淘汰同一批对象 | 连续达到恢复条件进入 Recover；截止时间到达则失败 |
| Recover | 仅单块或单项必要工作 | 按序消费并归还 | 必要申请按新样本批准，可选保留仍关闭 | 恢复后的工作退休、新样本健康且冷却结束后进入 Normal；再次不足立即 Drain |

收到原生 Low/Critical 时立即发出一次 trim 请求。普通 `A<R` 时先关闭新工作准入，持续 500 ms 后发出 trim。原生严重压力可以在当前压力周期中追加一次升级事件，禁止每次采样重复生成全量淘汰请求。

压力收缩不使用 `Km`。收缩动作直接对应暂停新增、解除可选引用和等待生命周期结束。删除旧内存控制器通过减半计算并发、严重时设计算并发为 1 的逻辑。

`Drain` 不以持有 `HeavyPhaseLease` 本身作为“仍在计算”的证据。driver 可能正持有阶段凭证、等待该阶段的连续存储。应结合实际排队/运行任务及申请位置判断可停留边界。

压力或必要容量等待开始时建立唯一的等待截止时间。重复采样、阶段凭证仍存活、重试预约和重新发布相同需求均不重置截止时间。真正恢复准入并推进目标工作后结束该次等待周期。30 s 到达时发布 failure 并开始取消收束；正在进行的不可中断第三方调用可能延长清理完成时间。

当 CPU 节流导致已接纳任务暂时停留时，内存控制器仍按真实内存条件判断。记录两个阻塞原因；禁止内存控制器擅自提高 CPU 额度以加快释放。

## 8. 各类存储的接入与释放规则

| 对象/路径 | 必要申请位置及申请量 | 压力下的行为 |
|---|---|---|
| `DecodeBlockMemoryPlan`、`DecodeBlockWorkspace` | driver 在读入前使用布局的输入/输出/临时区域总量，扣除已独占取得的可复用 backing | 关闭新增槽位；已预约块完成、提交、转移或析构 |
| 编码数值块、属性块与 reference 工作区 | 沿用现有槽位和工作区布局，确定受控输入、输出及临时容量；禁止用平均每线程内存推算 | 不新增块；原有块继续按所属凭证完成 |
| `ByteStoreSession::CreateSizedStore` 的连续存储 | driver 发布完整 `byteSize`，共存的旧 owner 仍保留在 `B` | 可在分配前有期限等待；已分配数据由 owner 生命周期释放 |
| `MemoryStore` 扩容 | driver 可准备时提前请求新数组完整容量；复制旧数据期间同时持有新旧 lease | 不能回收仍被复制或读取的旧数组；worker 内缺少必需许可时失败 |
| `EncodeLeafWorkspace` 的参数、几何、拓扑、属性 transfer store | 通过已绑定的 ByteStoreSession 接入，workspace 本身不另建额度池 | 各阶段消费者完成后释放；仍要提交的数据属于必需存储 |
| Morton 重排结果及其排序数据 | 复用现有受控 store/明确容量路径，在阶段分配边界请求；直接终端申请按第 9 节处理 | 不淘汰正在使用的 remap；可选 key cache 不触发增额 |
| `ScratchByteBufferPool` 中空闲固定 backing | 保留时已有 lease 仍计入 `B`，复用不重复预约 | 禁止新增留存，在池锁外析构可释放 backing |
| scratch 中既有豁免 vector | 继续按现有清单边界处理 | 可以释放池中自有空闲对象；不补造受控字节或物理释放统计 |
| encoded input / decoded frame LRU | 当前缓存开关和条目规则继续有效，不获得单独的预算份额 | 顺序解除可选缓存引用；消费者仍持有的数据继续有效 |
| 跨块/跨帧 reference | 依赖执行顺序决定必要生命周期，容量通过现有 store 预约 | 当前请求仍需要的引用保留；可选缓存入口可解除，最后 owner 决定实际释放 |
| lazy decode 已保留结果 | 会话持有的必要数据计入 `B`；新属性申请包含既有状态 | 后续实际请求重新采样；不销毁仍对外有效的数据 |
| 完整内存编码结果及连续化副本 | 在拼接/复制边界检查完整新目标及旧分段共存量 | 无法批准时失败；不自动改变用户要求的输出类型 |
| 已明确允许的范围读取文件存储 | 沿用当前 Ranged 后端选择契约，在实际分配前决定后端 | 可以按既有能力选择文件；实际 malloc/new 失败直接进入 failure |
| 借用输入、宿主接管后的输出、第三方内部存储 | 不接入新的分配审计和 lease | 系统观测自然包含其影响，控制器不直接释放这些数据 |

恢复后仅重新允许缓存策略，不主动重建此前淘汰的缓存。某个可选对象已经被当前任务实际依赖后，其释放必须遵守消费者生命周期。

LRU 删除入口、lease 归还、实际数组析构、系统可用物理内存上升是不同事件。诊断分别报告，不推断它们同步发生。

## 9. 申请准入、不能等待的点与失败

所有可等待的新必要申请都在 driver 的安全边界进入同一条路径：

```text
计算确定的 N
→ 服务 driver 回收事件
→ 检查模式、停止状态与内存准入
→ 尝试现有额度预约
→ 发布必要需求并唤醒控制器
→ 控制器使用新鲜物理样本批准、等待或拒绝
→ 原子取得容量 lease 与对应任务凭证
→ 实际分配
```

`CheckNecessaryCapacity` 是判定/需求登记入口，成功返回不代表已经发出 lease。实际申请仍需以最终预约结果为准。所有等待都释放执行锁和容量锁，并服务 trim 事件与取消。普通块准入由 `RunOrderedBlocks` 持续消费顺序完成的结果；已经进入提交函数的存储申请保持当前提交边界，不递归提交后继结果。

`RequiredContinuation` 必须区分当前槽位与可推进的终端任务。提交函数仍持有自己的槽位，该槽位的归还依赖当前提交完成，不能被算作可等待的释放来源。此时只等待实际排队或运行的终端任务；这些任务结束后，Fixed 的必需容量仍不足即报告 failure。Adaptive 继续按新物理样本判断许可，并保留同一等待截止时间。超过绝对能力的整笔需求立即失败。

合法的 Ranged 文件后端选择会撤销其内存需求；Normal 状态同时清除该需求的等待周期，避免已撤销申请产生后续超时。压力周期的截止时间继续遵循第 7 节。

`CreateSizedStore` 的 driver 分配不能仅因为旧额度能预约就绕过已经关闭的内存准入门。块准入、阶段必要存储以及明确的连续增长共用同一份内存状态。

| 情况 | 确定处理 |
|---|---|
| `N` 可由已有工作释放、环境余量恢复或新许可满足 | 在 driver 安全边界有期限等待 |
| `N` 超过增长系数/普通步长，满足 `N<=F` | 按整笔必要申请批准，不拆基础块、不等待自己释放 |
| `N>C`，或排空后必需共存容量加 `N` 仍超过 `C` | 立即通过 failure 报告不能满足 |
| 当前长期占用导致余量不足，可选数据已回收 | Hold；截止时报告目标余量无法恢复及必要申请信息 |
| 已运行 worker 的受控增长无法预约 | 立即通过 failure 收束；禁止 worker 等待同池子任务、driver 或未来消费者 |
| 可选缓存无法取得许可 | 不建立该缓存，正常执行其既有无缓存路径 |
| Ranged 数据在分配前选择允许的文件后端 | 按既有后端选择算法执行，记明选择原因 |
| 实际数组分配失败、尺寸溢出、文件读写失败、布局错误 | 立即通过既有 failure 收束，不重试替代模式或临时修改目标 |

应迁移的直接申请点集中在 `CreateSizedStore`、driver 可执行的 `MemoryStore` 增长准备、现有工作区准入以及实际使用的重排存储路径。worker 中能够提前确定的必要受控容量在准入前预留。不能提前确定的增长保留明确失败语义，不引入等待式分配器，也不以扩大豁免清单掩盖该问题。

完整解码最低容量分析继续复用 `AnalyzeDecodeStorage` 和 `DecodeSession::AnalyzeAttributeStorage`。分析结果属于受控路径门槛，不能直接作为 `M` 的强制下限，更不能强制突破物理余量目标。分析发现全内存路径门槛高于 `C` 可以提前说明不可行；其他实际允许的文件后端路径遵守各自契约。

## 10. CPU 与内存控制的合流

当前 `DataCodecCpuController`、`CpuPermitBudget` 和 `CodecThreadMode` 已实现独立 CPU 控制。内存 Km 参照其有期限估计和限幅更新流程，在原内存控制器中维护独立状态；两者分别定义采样量、公式和调控对象，具体对应关系见第 11 节。

1. 内存控制器发布 `M`、内存准入门、可选留存状态和恢复阶段槽位约束。
2. CPU 控制器发布 CPU 时间额度及计算许可。
3. 根执行对象在同一执行锁下合并，再通过既有通知唤醒 driver/worker。
4. 普通块需同时通过内存准入、槽位准入及 CPU 准入；已完成结果的提交与清理不消耗新的计算许可。
5. 内存控制器不写 CPU 的 Q、K 或目标空闲比例，不通过物理余量推算线程数。
6. 内存/输入/输出等待向 CPU 控制器提供 `growthBlocked`，防止闲置期间放大 CPU 额度。
7. 内存 Recover 采用单槽位。恢复结束回到现有由执行能力决定的有界槽位目标，不增加独立的槽位增益学习。
8. 仅内存 Adaptive 启用时也必须能够自动采样，不能再用 `sample.threaded` 表示内存观测是否有效。Windows 单计算线程仍可使用控制线程。
9. 任一自动模式需要控制线程时，复用同一个控制线程；CPU 与内存各自维护采样时钟、样本有效性和原因字段。
10. Unlimited 内存与 CPU Adaptive 组合不创建内存压力控制；Fixed 内存不因本方案自动改变其字节额度。

低层已发出的内存 lease 与已开始的终端任务不受控制器参数变化撤销。计算许可、内存许可、任务生命周期和失败清理的正确性独立于 CPU K 和内存 Km 的估计结果。

## 11. 关于内存 K 的正式决议

### 11.1 与当前 CPU 实现一致的机制

内存采用“名义增益立即运行、正常工作中的短窗口估计、数值有效时限幅更新、后续正常事件继续更新”的机制。初始 `Km = 1/2`，估计结果影响提前开放的许可窗口。压力收缩继续执行第 7 节的离散动作，不新增收缩 K。

| 机制 | 当前 CPU 代码 | 本方案的内存约定 |
|---|---|---|
| 初始值 | 收缩 0.5、增长 0.125 | Km 为 0.5，仅用于增长窗口 |
| 首次观测 | 两个 200 ms 窗口，中间一次小幅降低 Q | 两个 250 ms 窗口，中间一次缩小普通增长的提前许可部分 |
| 估计输入 | 系统空闲比例变化和计算额度变化 | 系统可用字节变化和观测段内实际成功发出的新预约字节 |
| 增益更新 | `K = clamp(α/g, 0.025, 1)` | `Km = clamp(αm/gm, 0.025, 1)` |
| 首次期限 | 从开始测量起 1 s | 从开始测量起 1 s |
| 数值无效 | 保留现有增益 | 保留现有 Km，首次没有结果时继续使用 0.5 |
| 后续更新 | 普通 Q 调整后的观测 | 普通必要增长后的观测 |
| 校验范围 | 样本、数值、基本执行状态和额度边界 | 样本、字节计数、基本执行状态和许可边界 |

两者的 K 均属于有界启发式控制参数。当前 CPU 代码没有对负载归因或估计准确性进行检验，内存方案遵循同一约定，不加入稳定工作类型、主导瓶颈判断、外部负载稳定性、置信度或第三个准确性确认窗口。

### 11.2 内存响应量与公式

内存 M 表示分配许可。减少未预约许可不会立即释放页面，增加许可也可能尚未用于分配。因此内存响应使用实际成功发出的新预约量关联系统观测：

```text
A0 = 基线窗口内有效系统可用字节样本的平均值
A1 = 响应窗口内有效系统可用字节样本的平均值
D  = 基线窗口结束至响应窗口结束，经必要申请准入路径成功发出的新预约字节之和
gm = -(A1 - A0) / D
Km新 = clamp(αm / gm, 0.025, 1)
αm = 0.5
```

`D` 来自执行根已有的需求与成功预约事件，作为单个测量段的确定输入计数。在发出 lease 时累计该 lease 实际取得的确定容量。`MemoryStore` 扩容会先提出必需容量 N，并可在当前已有许可内取得较大的增长容量；此时 D 使用最终 lease 容量，实际新数组使用相同容量。失败预约、单纯修改 M、lease 拆分/移交和 backing 复用均不增加 D。测量结束后清空活动计数，固定快照保留本次结果，不建立逐分配审计记录。它也不使用两个时刻的 `B` 差值，期间归还的旧 lease 不抵消已经发出的新预约。

`gm` 表示该段时间观测到的“系统可用量下降/新预约字节”，不表示已精确识别的物理分配倍率。页面延迟触碰、旧数据释放和外部程序均可能影响 A；这些影响直接体现在观测结果中，不增加因果判别代码。`Km` 始终只改变第 6 节的提前许可项，确定容量预约和系统观测继续分别记录。

禁止用 `-ΔA/ΔM` 把许可变化解释为物理消耗，也禁止将 gm 或 `D×gm` 写入实际内存占用合计。`N<=F`、能力边界 C、原生压力门控和生命周期约束继续使用原有确定量及系统样本，不使用 gm 折算必需申请的字节数。

### 11.3 首次短测量流程

1. 请求启动时设置 `Km=0.5`、`gainSource=Nominal` 和 `calibration=Pending`，立即进入正常执行。
2. Normal 状态存在真实必要增长需求且物理样本有效时，进入 Measuring，固定截止时刻 `startedAt+1 s`，开始 250 ms 基线窗口。正常工作、提交、回收和采样照常推进。
3. 基线窗口结束后，对下一笔通过第 6 节条件的普通增长使用一次 `P试探=floor(0.75×min(floor(Km×F),S))`，其许可公式为 `W=min(F,max(N,P试探))`。只缩小提前开放部分；原子必要申请仍完整保留。`RequiredContinuation` 继续使用 W=N，不承担试探动作。
4. 首次试探对应的新预约成功后开始 250 ms 响应窗口，持续累计 D 和采样。基线结束后的等待计入同一个 1 s 截止时间。窗口不足以在截止前完成时，本次结果为 TimedOut。
5. 两段各有有效样本、`D>0` 且算术有效时计算 gm。gm 有限且 `gm>=1e-6` 时，发布限幅后的 Km，记录 Estimated。其他数值结果记录 Unusable，保留现有 Km。
6. 到期、请求结束或取消立即结束测量；到期记录 TimedOut，提前结束或取消记录 Unusable 并附对应原因。遇到内存压力、样本失效或 T/C 变化时终止当前测量对，记录 Unusable，并执行原有压力或失败路径。期限和基本状态检查先于估计发布。

收集两个窗口的目标耗时约为 500 ms，实际耗时还包含等待合法申请和采样调度。1 s 表示首次尝试的截止时间，控制线程在下一次运行时检查并结束已到期的尝试，不接受截止后的样本补齐结果。它不保证每个请求都有足够的新预约，也不保证短时间能得到准确 Km。没有可用结果时继续正常处理请求，不启动额外分配、页面触碰、缓存重建或专用基准任务。

### 11.4 后续更新与检查边界

首次尝试结束后，新的普通必要增长可以利用最近的 250 ms 有效样本作为基线，在新预约成功后的 250 ms 窗口再次计算 gm 并更新 Km。后续使用正常增长，不追加主动试探，每个观测对只计算一次，同一时刻最多维护一个测量段。样本不足、D 为零或数值无效时丢弃该段并保留现有值。压力、取消和能力变化同样结束该段。

全部检查限于可直接读取的信息：请求是否活动或停止、内存状态、是否存在明确需求和成功预约、样本序号与时间戳、T/A/C 的合法范围、D 的溢出保护，以及除法结果的有限性、方向和限幅。字节差值先转为可表示负值的计算类型，再求 `A1-A0`。不检验“这笔预约已经全部触碰物理页面”“CPU/I/O 是否主导”“两次执行是否同等负载”之类准确性条件。

新 Km 仅在后续合法增长时生效，不为应用新 Km 单独创建增长事件，也不绕过 grantEpoch、增长间隔、RequiredContinuation 或等待截止规则。初次无效使用名义增益、后续无效保留已有增益属于算法的正式分支；真实分配失败、容量溢出及执行错误继续进入 failure。

比例、字节边界由设备观测及确定需求计算。αm、名义 Km、增益限幅、观测窗口、试探幅度、恢复确认、滞回和许可步长是集中声明的策略参数。运行时估计用于调整响应强弱，参数普适性仍需 Windows 实测。本轮不暴露这些内部参数的动态接口，不增加逐设备性能预设。

## 12. 共用模块的具体改造边界

| 模块 | 应实施的改造 |
|---|---|

## 13. 诊断字段与验收口径

复用现有事件环、资源快照和 JSON 报告，增加以下内存字段：

- 配置：`targetAvailableMemoryRatio`。
- 观测：`physicalTotalBytes`、`availablePhysicalBytes`、目标 `R`、恢复水位 `H`、样本年龄及各环境剩余量。
- 执行：`reservedBytes B`、`currentLimitBytes M`、`unreservedAllowanceBytes U`、`absoluteCapacityBoundBytes C`。
- 需求：`nextRequiredBytes N`、所有者、阶段、`RequiredContinuation` 标志、grantEpoch。
- 状态：内存准入门、压力状态、等待起点、截止时间、最近决策原因、最近回收完成事件。
- 增益：`memoryGain Km`、`memoryResponse gm`、`gainSource=Nominal/Observed`、`calibration=Pending/Measuring/Estimated/Unusable/TimedOut`、测量起点/耗时/截止、A0/A1/D、更新次数及观测终止原因。无有效 gm 时输出 null，Estimated 仅表示形成观测值。

新增原因明确区分 `ReserveTargetLow`、`NativeMemoryPressure`、`RuntimeHeadroomLow`、`RequiredGrowth`、`RequiredContinuation`、`SampleUnavailable`、`RetainedStoragePreventingProgress` 和 `WaitDeadlineExceeded`。名称在实施时统一加入现有枚举与格式化函数，不新增并行日志系统。

正常样本只更新固定快照。日志在状态转移、额度变化、增益更新、测量结束、异常和请求结束时输出。未知物理样本不填零，不把容量承诺写入物理占用合计。

运行结果统计以以下口径衡量：

```text
目标缺口 = max(0, R - A)
目标不足持续时间 = 有效样本区间内 A < R 的时长
恢复时间 = 压力触发至满足恢复条件的时长
```

结果同时报告样本无效时长、最长不可中断工作、必要数据保留和外部负载无法恢复的情况。禁止把“系统没有恢复目标”一律归因为 Km 不正确。

## 14. 验证计划

实施完成后集中执行 Windows 核心和 Qt 测试，编译前加载用户指定的环境脚本。本方案不安排 WASM、跨平台或每完成一个小项即进行长程测试。以下保留完整验证目标，本轮执行结果与未覆盖边界在第 15 节逐项说明。

优先复用 `DataCodecFeatureResourceController`、`DataCodecStorageAnalysisTests`、执行机制测试及 Qt 资源控件测试。用可注入样本和可控时钟验证策略，不依赖实际机器发生低内存事件。

| 验证项 | 必须证明的结果 |
|---|---|
| 20% 物理分母 | Job/进程限制不会改变保留比例的分母，环境剩余量独立限制增长 |
| 大小设备与边界比例 | 安全算术、滞回合理、未知样本不进入增长 |
| Fixed / Adaptive / Unlimited × 两种 CPU 模式 | 内存和 CPU 参数独立，控制线程及门控组合正确 |
| 有额度、无真实需求 | 不预分配、不反复扩张 |
| 同一个旧样本反复唤醒 | 不重复授权同一份未观察到的余量 |
| 单笔 `N` 大于 Km 窗口或步长 | 满足 `N<=F` 时能获准，不被保守系数永远卡住 |
| Km 首次两个短窗口 | 真实需求触发一次提前许可缩小，正的有限 gm 按公式限幅更新，不追加准确性验证窗口 |
| Km 无有效响应 | D=0、余量不下降、方向异常或数值无效时保留增益，首次保留 0.5 |
| Km 首次 1 s 期限 | 等待申请不重置截止；长工作和不足样本以 TimedOut 结束尝试，正常任务无需等待估计成功 |
| Km 后续观测与请求复用 | 后续普通增长可更新已有增益，每个观测对仅处理一次；新请求从名义值重新开始 |
| Km 计数与审计分离 | M 变化、失败预约、lease 移交和 backing 复用不增加 D；旧 lease 归还不抵消 D；gm 不进入实际占用合计 |
| Km 边界与压力优先 | 极端观测始终限幅；压力、取消、样本失效、T/C 变化结束当前观测，保留原有准入/失败契约 |
| 连续存储的旧新共存 | 预约包含新数组全容量，旧数组在复制期间有效 |
| 阶段 RequiredContinuation | 等待不依赖自身或后继释放，无重复计入许可 |
| 余量骤降 | 新块停止接纳，已有 lease 可完成，顺序提交与取消可用 |
| 已有 B 超过新能力或额度 | 不撤销有效 lease，排空后作明确可行性判断 |
| LRU 仍有共享消费者 | 淘汰入口不使仍使用的数据失效，不虚报物理释放 |
| 解码长期输出阻止恢复 | 有期限等待并输出具体原因，不循环降额或擅自删结果 |
| CPU 额度为零、内存同时低 | 不互相修改目标，取消和提交不依赖新的 CPU 许可 |
| 实际分配/读取/写入失败 | 首错、取消唤醒、异常清理保持现有 failure 契约 |
| 恢复与再次波动 | 连续健康样本后单块恢复，抖动不重置等待截止时间 |
| Qt 比例与设置迁移 | 编码、解码均使用相同参数，旧 Adaptive 字节数不污染新比例 |

集成数据覆盖数值属性为主、拓扑为主、reference 依赖、lazy 属性补解、完整内存输出和文件输出。记录固定内存方案与新 Adaptive 在同一构建、相同输入、相同 CPU 模式下的耗时，以及物理余量时间序列。另在测试设施中比较保持名义 Km 与启用 Km 估计的吞吐、目标偏离、等待时间和必要申请拒绝情况，记录首次测量成功率与耗时；不增加产品层的第三种 Adaptive 子模式。实验不以主动耗尽整机内存为手段；压力分支优先使用合成样本验证。

完成这些检查后，才能将第 5 节参数标记为已验证。文档中的公式、状态机和生命周期契约是实现约定，当前不构成运行效果的测量结论。

## 15. 本轮实施与 Windows 验证记录

### 15.1 实施结果

在现有资源控制器、执行根与 ByteStore 中完成改造，复用已有容量 state、lease、线程池、事件环和消息通道。Adaptive 使用独立的 `targetAvailableMemoryRatio`，默认 0.20；旧 Adaptive 固定字节参数通过参数校验拒绝。Fixed 与 Unlimited 保留既有语义，CPU Fixed/Adaptive 保持独立。

Qt 编码与解码共用控件已增加比例输入，设置版本迁移为 2。迁移删除旧 Adaptive 字节额度，采用 20% 默认；当前模式的无效字段不继续保存。控件使用项目当前 Qt 5 的字段及标签显隐接口。

Km 由成功的新 lease 容量和物理样本驱动，首次 1 s 期限、后续被动观测、数值有效性检查及限幅已接入。必要存储、完整输出增长和块准入共用内存门控。压力状态采用 Normal/Drain/Hold/Recover，恢复阶段使用单槽位。诊断报告将物理余量、容量承诺、当前许可及未知值分别输出；额度事件的容量值从发布事务传入，事件记录不重复取得容量锁。

### 15.2 构建与功能验证

验证日期为 2026-09-12。环境脚本为用户指定的 `clion_env.ps1`；构建采用 MSYS2 UCRT64 Clang、CMake/Ninja、RelWithDebInfo（`-O2 -g -DNDEBUG`）。目标为 `iGameDataCodecTests`、`iGameDataCodecQtResourceTests`、`iGameVis`。

`ctest -R '^DataCodec\.' --output-on-failure` 的最终结果：13/13 通过，共 20.43 s。包含核心全集、解码容量分析、failure、存储所有权、Morton、拓扑、数值编码和解码、任务协调、执行机制、内存模式、CPU 控制及 Qt 资源控件。核心全集覆盖 reference、lazy 属性补解、内存输出及原生文件往返。

新增控制器用例使用合成物理样本和可控时钟，覆盖物理分母与 Job 分离、模式参数冲突、旧样本重复唤醒、必需大申请、阶段共存、压力确认与单次回收、单槽恢复、样本失效和 30 s 截止、能力缩小、Km 更新及终止条件。正响应夹具在合成时钟 750 ms 时得到 `gm=2、Km=0.25`，另验证 1 s 超时、无效/负响应、上下限、计数溢出和请求重置。这些时间属于控制器时序验证。

集中测试修复了提交扩容等待自身槽位归还的问题。数值和拓扑的容量不足用例现已正常失败并清理，取消等待用例正常唤醒。一个原生 polyhedron 测试在读取快照时遇到瞬时锁竞争，已按快照接口契约改为有界重试，原有容量和释放断言保持。

原始构建与测试记录位于仓库根目录的 `logs/memory-reserve-build-5.log`、`logs/memory-reserve-ctest-final.log`，日志按现有仓库忽略规则保留在工作区。
